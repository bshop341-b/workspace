## Ditto infra and UI fixes
- Fixed `https://api.ditto.local/v1/posts` 404 by removing the bad ingress patch from `github/argocd/values/ditto/platform/kustomization.yaml`; commit `2aa61eb` (`fix(ditto): preserve api ingress paths`). Root cause was `values/ditto/platform/ingress-patch.yaml` overwriting `spec.rules` and deleting `http.paths`.
- Ditto required MongoDB transactions, so local `ditto-mongodb` was converted to a single-node replica set via GitOps before migration.
- Migrated Ditto from local MongoDB to MongoDB Atlas after Atlas allowlisted cluster egress IP `189.223.37.53/32`. Verified Atlas connectivity from inside the cluster, switched `app-secrets` `MONGO_URI` live, restarted all `*-ditto-apis-deployment`, and confirmed health plus register/create-post flows still worked.
- Removed the local MongoDB Argo app from `github/argocd/applications/ditto/kustomization.yaml`; commit `8bb6d14` (`chore(ditto): remove local mongodb application`). Argo dropped the app but left deployment/service behind, so those were deleted manually.
- UI did not show new posts even though API returned them because the Next.js/Node server-side fetches to `https://api.ditto.local` failed TLS verification (`UNABLE_TO_VERIFY_LEAF_SIGNATURE`). Applied a workaround in `github/argocd/values/ditto/ui/values.yaml` by setting `NODE_TLS_REJECT_UNAUTHORIZED="0"`; commit `3581a99`. Also noted the UI home/feed uses a ~300s cache/prerender window, so fresh posts may take up to 5 minutes to appear.

## Ditto UI runtime patch follow-up
- Because the frontend source/build pipeline for `ghcr.io/rfcku/vora-web:main` was still unavailable and the UI kept calling relative `/posts` URLs from the browser, the working fix was to vendor the UI Helm chart into `github/argocd/charts/ditto/ui` and repoint `github/argocd/applications/ditto/ditto-ui.yaml` to use that local chart instead of `rfcku/helm-charts`. This avoided a permissions block pushing to `rfcku/helm-charts`.
- Added `command`/`args` support to the vendored chart deployment template and configured `github/argocd/values/ditto/ui/values.yaml` to patch the standalone Next app on container startup before `node /app/server.js` runs.
- The startup patch fixes `server.js` when `nextConfig.env` is empty by injecting `NEXT_PUBLIC_API_URL=https://api.ditto.local/v1`, and rewrites `.next/static/chunks/*.js` so the client bundle falls back to `https://api.ditto.local/v1` for axios `baseURL` and to `https://api.ditto.local` for media instead of `localhost:9001`.
- Initial attempt used `sed -i` and failed because `/app` was not writable at the directory level inside the container, even though file contents could be replaced. Durable workaround: write to `mktemp`, then `cat "$tmp" > target` and remove the temp file.
- Commits for the runtime patch path: `8a469d9` (`fix(ditto-ui): vendor ui chart and patch api runtime`) and `058d186` (`fix(ditto-ui): patch startup files without sed -i`). After rollout, `application/ditto-ui` returned healthy and the served client chunk contained `baseURL:tp||"https://api.ditto.local/v1"`, indicating the browser bundle should stop falling back to `https://ditto.local/posts?...`.
- Final caveat: visual/browser validation from this environment remained blocked because `ditto.local` did not resolve locally and browser navigation was restricted, so the live confirmation came from inspecting the patched pod and served assets rather than opening the site directly.

## Ditto auth persistence follow-up
- The reported `ditto.local` auth persistence bug was traced to the backend, not just the UI. The frontend bundle does persist `token`, `user`, and `id` in `localStorage`, but on reload it validates the session with `GET /v1/users/me` and clears auth if that call returns `401`.
- Live API validation showed a fresh token from `POST /v1/auth/register` immediately failed on `GET /v1/users/me` with `401 unauthorized`, which explained why the UI appeared to "forget" login after refresh.
- Root cause in `rfcku/ditto`: auth middleware stores the authenticated user in Gin context as `user`, while `cmd/server/routes/handlers/users.go` (`Me`) and `cmd/server/routes/handlers/wallets.go` (`GetMyWallet`) were incorrectly reading `userID`. That context-key mismatch made those endpoints reject valid JWT-authenticated requests.
- A local backend fix was made in `~/.openclaw/workspace/github/rfcku/ditto` to read `user` with fallback compatibility for `userID`; local commit `6c65e0c` with message `fix(auth): use middleware user context in me and wallet handlers`.
- Separate durable repo discovery result: `~/.openclaw/workspace/github/rfcku/ditto-ui` did not exist, and attempts to clone `rfcku/ditto-ui` or `rfcku/vora-web` returned `Repository not found`. The running UI image still identifies itself as `vora-web`, so the actual frontend source repo is likely private, differently named, or under another owner. That means backend fixes were possible locally, but clean frontend-source changes still require locating the real repo or gaining access to it.
- User reported an additional Infonavit asset of `238,518 MXN`; updated `Presupuesto2026 v2` (`BALANCE`, `02_NET_WORTH`, `01_DASHBOARD`) and the Obsidian finance notes to reflect net worth above 1M MXN.
- User clarified the `238,518 MXN` Infonavit amount is a separate non-liquid asset, not deployable cash; relabeled it in the finance sheet and excluded it from the liquid-assets metric while still counting it in total net worth.
